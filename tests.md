**Сценарий 1. Успешный поиск аудиозаписи**
*   **Описание кейса:** Пользователь отправляет название песни, бот находит её и предлагает варианты.
*   **Интегрируемые модули:** Модуль взаимодействия с пользователем (`handlers.search_audio_by_name`), модуль внешних API (`api_utils.search_for_tracks`), модуль БД (`database_utils.log_interaction`).
*   **Изоляция (моки):** Успешный ответ `httpx.get` (список из 1-2 треков), успешный ответ `httpx.post` (БД).
*   **Ожидаемый результат:** Взаимодействие залогировано. API модуль корректно распарсил мок-ответ. Хендлер сформировал сообщение и inline-клавиатуру с найденными треками, состояние пользователя перешло в `SELECTING_SONG`.

**Сценарий 2. Поиск песни с пустым результатом**
*   **Описание кейса:** Пользователь ищет непопулярную песню, результаты не найдены.
*   **Интегрируемые модули:** `handlers.search_audio_by_name`, `api_utils.search_for_tracks`.
*   **Изоляция (моки):** Ответ `httpx.get` возвращает `{"results": []}`.
*   **Ожидаемый результат:** API утилита возвращает пустой список. Хендлер обрабатывает этот список и отправляет пользователю уведомление: "Ничего не получилось найти". Статус не меняется.

**Сценарий 3. Отказоустойчивость при падении микросервиса поиска (Негативный)**
*   **Описание кейса:** Пользователь делает запрос, но микросервис audio_receiver недоступен (HTTP 500).
*   **Интегрируемые модули:** `handlers.search_audio_by_name`, `api_utils.search_for_tracks`.
*   **Изоляция (моки):** `httpx.get` выбрасывает исключение `HTTPStatusError`.
*   **Ожидаемый результат:** API модуль перехватывает ошибку сети и возвращает `None`. Хендлер распознает `None` и сообщает пользователю об ошибке сервера без падения всего приложения.

**Сценарий 4. Выбор песни и формирование стартового меню**
*   **Описание кейса:** Пользователь нажимает на кнопку с понравившимся треком из результатов поиска.
*   **Интегрируемые модули:** `handlers.save_selected_audio`, `api_utils.get_track_info`, механизм состояний `context.user_data`.
*   **Изоляция (моки):** Ответ `httpx.get` с длительностью трека, например 180с.
*   **Ожидаемый результат:** Запрос к API возвращает длительность (180с). Хендлер сохраняет ID трека, длительность и базовые границы (0-60с) в модуль памяти пользователя. Генерируется главное меню с кнопкой создания кружочка.

**Сценарий 5. Изоляция отказов базы данных (Негативный)**
*   **Описание кейса:** При поиске пользователем песни база данных недоступна.
*   **Интегрируемые модули:** `handlers.search_audio_by_name`, `database_utils.log_interaction`.
*   **Изоляция (моки):** Запрос к audio_receiver успешен, а `httpx.post` к сервису БД падает по таймауту.
*   **Ожидаемый результат:** Модуль БД ловит исключение и возвращает `False`. Хендлер пишет в лог ошибку, но не прерывает процесс. Хендлер все равно отправляет пользователю результаты поиска аудио.

**Сценарий 6. Успешная установка произвольного таймкода**
*   **Описание кейса:** Пользователь отправляет текстовое сообщение с новыми границами обрезки в формате "30 75" (при заранее сохраненной в памяти длительности трека, например, 200 секунд). Бот успешно считывает границы, обновляет их и возвращает пользователю меню выбора дальнейших действий с подтверждением выбранного интервала.
*   **Интегрируемые модули:** Хендлер `handlers.set_custom_time`, встроенная утилита парсинга времени `handlers.get_seconds`, контекст пользователя `context.user_data`, механизм маршрутизации `Telegram (ConversationHandler)`.
*   **Изоляция (моки):** Без сетевых моков. Используются моки объектов `update` и `context` с предустановленной длительностью файла `(FILE_DURATION = "200")`. Функция `get_seconds` оборачивается патчем для отслеживания количества вызовов и переданных аргументов.
*   **Ожидаемый результат:** Хендлер корректно интегрируется с функцией `get_seconds`, вызывая её ровно два раза с аргументами "30" и "75". В `user_data` успешно обновляются значения `DURATION_LEFT_BORDER` ("30") и `DURATION_RIGHT_BORDER` ("75"). Бот отправляет сообщение с текстом "с 30с по 75с.", фразой "Выберите опцию:" и прикрепляет inline-клавиатуру, состоящую ровно из 3 кнопок. Функция возвращает `ConversationHandler.END`, происходит возврат в главное меню трека.

**Сценарий 7. Интеграция цепочки микросервисов при создании видео (Happy Path)**
*   **Описание кейса:** Пользователь жмет "Создать кружок" с дефолтными таймкодами.
*   **Интегрируемые модули:** `handlers.create_video_message`, 4 метода из `api_utils` (скачивание трека, обрезка, скачивание обложки, создание видео).
*   **Изоляция (моки):** Успешные ответы от `stream`, `trim_audio`, `download_cover`, `create_video` (моки файлов в файловой системе через `tempfile`).
*   **Ожидаемый результат:** Хендлер вызывает модули по цепочке. Файлы успешно модифицируются, передаваясь из модуля в модуль. Итоговое видео отправляется в Телеграм.

**Сценарий 8. Сбой микросервиса обрезки аудио (Негативный)**
*   **Описание кейса:** Пользователь запускает создание видео, но ломается `media_processor` на этапе обрезки.
*   **Интегрируемые модули:** `handlers.create_video_message`, `api_utils.trim_audio`.
*   **Изоляция (моки):** Мок для скачивания трека успешен. Мок для `trim_audio` возвращает HTTP 400 (например, неверный таймкод).
*   **Ожидаемый результат:** Модуль `trim_audio` возвращает `False`. Хендлер `create_video_message` прерывает дальнейшую цепочку (не качает обложку, не рендерит видео) и отправляет пользователю текст "Ошибка при создании кружка".

**Сценарий 9. Использование стандартного изображения при недоступности обложки аудио**
*   **Описание кейса:** Сервис скачивания обложек не смог найти обложку для трека, либо недоступен.
*   **Интегрируемые модули:** `handlers.create_video_message`, `api_utils.download_cover`.
*   **Изоляция (моки):** Моки трека/видео успешны. Мок `download_cover` возвращает пустую строку `""` или падает с ошибкой.
*   **Ожидаемый результат:** Хендлер обнаруживает отсутствие скачанной обложки и подставляет путь к стандартной обложке. Интеграция с модулем создания видео продолжается успешно, видео генерируется.

**Сценарий 10. Перезапуск процесса через команду /newsong на этапе настройки времени**
*   **Описание кейса:** Пользователь находится в процессе настройки времени для кружка (зашел в поддиалог `time_conv_handler`), но передумал и отправляет команду `/newsong`. Бот должен корректно прервать текущий вложенный диалог, очистить память (`user_data`) и вернуться в начало для ожидания названия песни.
*   **Интегрируемые модули:** хендлер `restart_conversation`, `clear_user_data` (сброс памяти), механизм маршрутизации состояния (возврат в `st.TYPING_SONG_NAME`).
*   **Изоляция (моки):** В данном сценарии тестируется интеграция внутренних механизмов Telegram `ConversationHandler` (родительский и дочерний) и логики менеджера состояний бота. Внешние API-вызовы мокать не требуется, так как они не происходят при вызове `/newsong`.
*   **Ожидаемый результат:** Функция очистки удаляет из `context.user_data` переменные трека и времени (предотвращая утечку состояний в новый поиск). Бот отвечает "Введите название песни для поиска:" и возвращает состояние `st.TYPING_SONG_NAME`, которое корректно пробрасывается вверх в главный `handler`.
